# CleanSight 异构模型训练与评估框架需求文档

## 1. 文档目的

本文定义 CleanSight 模型仓库在训练与评估方面需要解决的问题、职责边界和能力要求。

本文只描述需求和总体思路，不规定：

- 代码目录结构；
- 类、接口或函数设计；
- 配置文件 schema；
- CLI 命令形式；
- 具体框架、数据库或存储选型；
- 迁移和实施步骤。

上述内容在后续设计阶段确定。

---

## 2. 背景

CleanSight 当前同时维护多类异构模型：

- 单帧、无状态的目标检测模型；
- 基于上游特征进行时序推理的 GRU；
- 基于上游特征进行时序推理的 Transformer；
- 基于上游特征进行时序推理的 causal-TCN；
- 离线处理完整序列的时序模型；
- 实时滑窗或有状态运行的时序模型。

这些模型之间存在明显差异：

- 输入形态不同；
- 推理方式不同；
- 状态和窗口语义不同；
- 适用指标不同；
- 是否需要性能测量不同；
- 训练和评估所需参数不同。

同时，同一种模型架构还会产生多个变体，例如：

- 输入特征维度不同；
- hidden size、层数、head 数不同；
- 参数量不同；
- 特征来源或特征 schema 不同；
- 训练超参数不同；
- 离线和实时执行方式不同。

如果所有模型分别维护完整训练和评估脚本，会产生大量重复；如果强行使用同一套训练和评估逻辑，又会掩盖不同模型的真实语义。

因此，本仓库需要建立一层适度的训练与评估框架：共享稳定且语义一致的流程能力，同时保留各模型和各执行模式的独立实现空间。

---

## 3. 仓库职责边界

### 3.1 本仓库负责

本仓库负责：

1. 定义和实现模型架构；
2. 组织模型训练；
3. 保存训练过程产生的 checkpoint 和运行结果；
4. 对 checkpoint 执行适用的模型评估；
5. 产出结构化指标、明细结果和评估矩阵；
6. 记录解释评估结果所需的运行信息；
7. 向外部模型管理仓库提供稳定、可消费的评估产出。

### 3.2 本仓库不负责

本仓库不负责：

- 正式模型版本号分配；
- release candidate 管理；
- 模型晋升和发布；
- 不可变模型版本库；
- 线上版本状态管理；
- 跨仓库的模型生命周期管理；
- 自动决定模型是否达到业务要求；
- 自动决定模型是否上线。

以上职责由外部模型管理仓库或人工流程承担。

### 3.3 与模型管理仓库的关系

本仓库的终点是“产出一次可解释的训练或评估结果”。

模型管理仓库可以选择其中某个 checkpoint 及其评估结果，用于后续版本冻结、审阅、发布和追溯。

两个仓库之间应通过稳定的结构化产出交互，不要求模型管理仓库理解本仓库内部的训练或评估实现。

## 4. 核心原则

### 4.1 训练完成后可以直接评估

框架不得在训练和评估之间引入不必要的候选创建、审批或发版步骤。

基本使用路径应保持为：

```text
训练 → 选择 checkpoint → 运行评估 → 查看结果
```

需要进入模型管理流程时，再由外部模型管理仓库消费评估结果。

### 4.2 共享流程，不强行共享模型语义

框架应共享以下类型的能力：

- 运行组织；
- 配置解析；
- 日志和环境信息记录；
- checkpoint 管理；
- 评估结果组织；
- 评估矩阵生成；
- 通用的完整性检查。

框架不应强行统一：

- 不同任务的数据语义；
- 不同模型的 forward 过程；
- 检测与时序指标；
- 离线与实时推理过程；
- 模型特有的状态管理；
- 不适用于某类模型的性能测试。

### 4.3 通过配置表达同架构变体

架构相同、仅模型规模或超参数不同的模型变体，不应复制训练和评估实现。

下列变化原则上属于同一模型实现的不同配置：

- 输入维度；
- hidden size；
- 网络层数；
- attention head 数；
- dropout；
- 参数量；
- batch size；
- learning rate；
- 窗口长度；
- 其他不改变基本输入输出语义的超参数。

只有当模型的网络结构、输入输出契约、状态语义或推理方式发生实质变化时，才应新增模型实现或执行策略。

### 4.4 上游能力抽象为特征来源

时序模型依赖的是上游特征，不是固定依赖某一种 YOLO 实现。

框架应能够描述：

- 特征来自哪里；
- 特征由什么方法生成；
- 特征的维度、字段和排列语义；
- 模型期望的特征 schema；
- 特征与模型输入是否兼容。

YOLO 是当前可用的特征提取方式之一，不应成为框架中的固定边界。未来应允许接入其他检测器、视觉编码器、手工特征或其他上游方法。

### 4.5 代码只产出评估事实

本仓库可以计算并展示指标，但不存储业务门槛，不根据门槛自动产生质量判决。

代码可以判断：

- 评估是否成功执行；
- 结果字段是否齐全；
- 测试数据是否具有可评估样本；
- 预测与真值是否能够对应；
- 汇总结果是否与明细一致。

代码不得判断：

- recall 是否足够高；
- F1 是否达到上线标准；
- 延迟是否符合产品要求；
- 当前模型是否应该发布。

## 5. 概念层次

### 5.1 任务类型

任务类型描述模型解决的问题，例如：

- 目标检测；
- 时序分类或时序分割。

任务类型决定数据真值语义和可使用的指标族。

### 5.2 执行模式

执行模式描述模型如何接收输入并产生输出，例如：

- 单帧无状态；
- 离线完整序列；
- 实时滑窗；
- 实时有状态逐步推理。

执行模式决定窗口、状态、因果性和性能测量等评估要求。

### 5.3 模型族

模型族表示一套可复用的模型结构实现，例如：

- YOLO detection；
- GRU；
- Transformer；
- causal-TCN。

模型族负责表达真正的架构差异，不代表某一次训练结果。

### 5.4 模型配置

模型配置描述某个模型族的具体变体，例如输入维度、层数、hidden size 和 dropout。

多个配置可以复用同一模型族实现，并产生不同参数量的模型。

### 5.5 训练运行

训练运行表示某个模型配置在指定数据和训练参数下执行的一次训练。

一次训练运行可以产生多个 checkpoint。

### 5.6 评估运行

评估运行表示对某个 checkpoint，使用指定数据、特征、推理协议和指标进行的一次评估。

同一个 checkpoint 可以有多个评估运行，例如：

- 使用不同测试集；
- 分别执行离线和实时评估；
- 使用不同但明确版本的指标口径；
- 在不同硬件上进行性能测量。

### 5.7 评估矩阵

评估矩阵汇总多个评估运行的事实，用于横向查看不同模型、配置和执行模式的结果。

评估矩阵不代表所有模型必须拥有相同指标，也不产生跨任务综合得分。

---

## 6. 分层能力需求

### 6.1 框架层

框架层应提供与模型语义无关或语义完全一致的通用能力：

- 训练和评估运行的统一组织方式；
- 配置的加载、覆盖和有效性检查；
- 随机种子、设备和运行环境记录；
- 日志和运行状态记录；
- checkpoint 的保存、加载和基本元信息；
- 结果 artifact 的组织；
- 评估结果的公共信封；
- 评估矩阵汇总；
- 通用完整性检查。

框架层不得包含某一模型专属的 tensor 处理、状态逻辑或指标算法。

### 6.2 任务与执行模式层

任务与执行模式层应表达同一类问题中可复用的语义：

- 检测任务的数据、预测与指标语义；
- 时序任务的标签、mask、逐帧和逐段指标语义；
- 离线完整序列的推理组织；
- 实时滑窗的窗口推进、冷启动和 reset 语义；
- 有状态模型的逐步输入输出组织；
- 适用时的延迟和吞吐测量。

同一任务或执行模式下的不同模型族应尽量复用这些能力。

### 6.3 模型族层

模型族层只实现模型真正特有的能力：

- 构建网络；
- 模型 forward；
- 模型特有的 loss 或输出转换；
- checkpoint 与模型结构的兼容检查；
- 必要时的状态初始化和更新。

模型族层应通过模型配置支持同架构的不同规模，不应为每个参数量变体复制实现。

### 6.4 实验配置层

实验配置层负责表达：

- 选择哪个模型族；
- 模型规模与超参数；
- 使用哪个任务和执行模式；
- 数据和特征输入；
- 训练参数；
- 评估参数；
- 需要计算的指标。

新增同架构模型变体时，原则上只增加或修改配置。

---

## 7. 训练能力需求

### 7.1 通用训练能力

框架应支持：

- 从模型族和模型配置构建模型；
- 从任务定义构建训练数据；
- 执行训练、验证和 checkpoint 保存；
- 记录实际使用的完整配置；
- 记录模型参数量；
- 记录训练数据和特征输入信息；
- 保存后续可以正确重建模型的必要信息。

### 7.2 模型变体

同一模型族的不同参数量应满足：

- 使用同一份模型实现；
- 使用同一训练入口；
- 通过配置表达结构差异；
- 每次训练独立记录解析后的模型配置；
- checkpoint 能够确认自身对应的模型配置；
- 评估时不能因使用错误配置而静默加载。

### 7.3 特征输入兼容性

使用特征输入的模型应检查：

- 特征 schema 与模型期望是否一致；
- 特征维度是否一致；
- 标签映射是否一致；
- 序列和样本标识是否可用；
- 不兼容输入是否能够在训练开始前被发现。

---

## 8. 评估能力需求

### 8.1 直接评估

训练产生的任意 checkpoint 都应能够直接启动适用的评估，不要求先进入模型管理流程。

评估应尽可能从 checkpoint 和训练运行中恢复模型构建信息，减少人工重复填写和配置错配。

### 8.2 按任务选择指标

评估应根据任务类型选择适用指标：

- 检测模型使用 mAP、precision、recall 等检测指标；
- 时序模型使用 accuracy、edit、segmental F1 等时序指标；
- 不适用的指标应标记为不适用，而不是赋值为零。

指标必须明确自己的计算口径和必要参数。

### 8.3 按执行模式选择评估方法

离线完整序列与实时滑窗评估应分别反映实际执行语义。

实时评估应能够描述：

- 每个时刻能够看到的输入；
- 窗口长度和推进方式；
- 状态何时清空；
- 冷启动如何处理；
- 是否包含平滑、投票或迟滞后处理。

不得使用离线全量推理结果冒充实时推理结果。

### 8.4 性能测量

是否需要测量延迟或吞吐，由执行模式和评估目的决定。

- 实时上线模型通常需要性能测量；
- 离线模型不强制提供实时延迟；
- 性能结果必须能够解释其硬件、batch、窗口、预热和统计方式；
- 性能指标只作为事实输出，不自动与业务门槛比较。

### 8.5 评估明细

用于正式比较或交付的评估运行，应保留足以解释汇总指标的明细结果。

检测评估应能够追溯到逐图预测；时序评估应能够追溯到逐序列或逐帧预测。

开发阶段的快速检查可以只保留摘要，但不得与正式完整评估混淆。

---

## 9. 评估矩阵需求

### 9.1 汇总内容

评估矩阵至少能够展示：

- 模型族；
- 模型配置或实验标识；
- 参数量；
- checkpoint；
- 任务类型；
- 执行模式；
- 测试数据；
- 特征来源和 feature schema；
- 适用的核心指标；
- 性能指标（适用时）；
- 评估完整性；
- 对应评估运行。

### 9.2 异构指标展示

评估矩阵必须允许不同模型拥有不同指标列。

- 不适用的字段显示为 `N/A`；
- 缺失或运行失败不能伪装成 `N/A`；
- 同名但口径不同的指标必须能够区分；
- 不对 mAP、F1、edit 等异构指标生成统一综合分数；
- 可以展示相同模型族或相同任务下的历史差异，但不自动解释优劣。

### 9.3 机器消费

评估矩阵必须同时支持人读和机器读取。

外部模型管理仓库应能够通过稳定格式读取矩阵和单次评估结果，而不依赖本仓库内部实现。

---

## 10. 完整性与错误处理需求

框架应区分三类情况：

1. 指标不适用于当前任务；
2. 指标适用，但评估所需输入缺失；
3. 指标适用且已成功计算。

完整性检查应能够发现：

- checkpoint 与模型配置不兼容；
- 特征 schema 与模型输入不兼容；
- 测试数据缺失或类别不可评估；
- 预测与真值无法对齐；
- 评估结果缺少必要字段；
- 指标口径或参数未声明；
- 实时评估缺少必要的窗口或状态语义；
- 报告数字与结构化结果不一致。

完整性检查的结果只描述评估是否可解释，不描述模型是否达到业务要求。

---

## 11. 可扩展性需求

### 11.1 新模型变体

新增同一模型族的参数量或超参数变体时，应主要通过配置完成，不应复制训练和评估代码。

### 11.2 新模型族

新增模型族时，只需实现该模型真正特有的构建、forward、loss、输出转换或状态能力，并复用已有任务和执行模式能力。

### 11.3 新任务类型

新增任务类型时，可以增加新的数据、预测和指标语义，不要求修改已有模型族的无关实现。

### 11.4 新执行模式

新增执行模式时，可以增加对应的推理组织和证据要求，不应迫使其他模式实现不适用的接口。

### 11.5 新特征提取方式

新增特征提取方式时，应通过通用特征来源和 feature schema 接入，不应要求修改时序模型的核心网络实现。

---

## 12. 非功能需求

### 12.1 可复现性

训练和评估结果应记录足以解释本次运行的配置、数据、特征、代码和环境信息。

### 12.2 可追溯性

评估矩阵中的每个数字都应能够定位到具体评估运行及其指标口径。

### 12.3 可测试性

框架公共能力、模型实现、任务指标和执行模式都应能够被独立测试。

### 12.4 易用性

常规训练后评估不应要求使用者理解模型管理或发版流程。

### 12.5 渐进采用

框架应允许现有模型逐步接入，不要求一次性重写全部训练和评估代码。

---

## 13. 验收标准

当以下场景均能成立时，可认为需求得到满足：

1. GRU 的 20D、64D、不同 hidden size 和层数变体复用同一训练与评估实现；
2. Transformer 和 causal-TCN 可以复用时序任务指标，但保留自己的模型实现；
3. 同一时序 checkpoint 可以分别执行离线和实时评估，并明确区分两种结果；
4. YOLO 检测不需要实现时序接口，也不会被要求计算时序指标；
5. 实时模型能够记录窗口、reset、冷启动和必要的性能结果；
6. 离线模型不会因统一格式而被迫产生虚假的实时延迟；
7. 特征提取器可以从 YOLO 替换为其他实现，而时序模型只依赖稳定的 feature schema；
8. 所有评估结果可以汇总到同一个异构评估矩阵；
9. 评估矩阵中的不适用、缺失和成功计算能够明确区分；
10. 外部模型管理仓库能够读取评估产出，而不需要 import 本仓库的内部代码；
11. 代码中不存在基于业务门槛的自动发版或达标判断；
12. 新增同架构参数量变体时，不需要复制训练或评估脚本。

---

## 14. 非目标

本阶段不要求：

- 建设完整 MLOps 平台；
- 建设模型 registry；
- 实现线上部署；
- 实现自动模型选型；
- 实现自动发布决策；
- 统一所有模型的指标；
- 消除所有重复代码；
- 确定最终目录结构和接口；
- 确定具体配置格式；
- 完成现有代码迁移。

本阶段的目标是先确认正确的职责边界和抽象粒度，再进入具体技术设计。

---

## 15. 后续设计阶段需要回答的问题

后续设计应基于本文进一步明确：

1. 框架层、任务层、执行模式层和模型族层的具体接口；
2. 模型配置、训练配置和评估配置如何组织；
3. checkpoint 中必须保存哪些重建信息；
4. feature schema 如何定义和校验；
5. detection 与 temporal prediction 的标准结构；
6. 指标实现如何版本化；
7. 离线和实时 evaluator 如何复用公共能力；
8. 评估矩阵的机读 schema；
9. 本仓库与模型管理仓库之间的交付协议；
10. 现有 YOLO、GRU、Transformer 和 causal-TCN 如何渐进迁移。
