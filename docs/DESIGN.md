# CleanSight 模型仓库设计准则

> 面向：在本仓库新增模型、改动评估框架、或进行重构的人。
> 本文是仓库级的抽象取舍准则，与具体框架实现解耦；框架的用法与接入见
> [`../framework/README.md`](../framework/README.md) 与 [`MODEL_ONBOARDING.md`](MODEL_ONBOARDING.md)，
> 需求边界见 [`TRAIN_EVAL_REQUIREMENTS.md`](TRAIN_EVAL_REQUIREMENTS.md)。

## 0. 架构底座：两纵一脊

本仓库整合三类异构模型（单帧检测、实时滑窗时序、离线全量时序）的训练与评估，落地为“两纵一脊”
的结构：

- **framework 脊柱**（`framework/cleansight_eval/core/`）：与模型语义无关的运行能力，包括 run
  组织、配置解析、环境记录、checkpoint 自描述、Pipeline 注册和 `PredictionOutput`。
- **benchmark 真源**（`benchmark/core/` + `benchmark/evaluators/`）：统一拥有指标口径、固定
  testset、`EvaluationResult v2`、prediction artifact schema、报告、矩阵、交付清单和评测 CLI。
- **两纵**（`temporal/`、`detection/`）：各自实现训练和 `predict()`，只产模型执行事实，不组装正式指标。
- **组合根**（`benchmark/cli/eval.py`）：从 framework 注册表取得 Pipeline，执行
  `framework predict → benchmark evaluator → persist/report/delivery`。

评测依赖方向固定为 `benchmark → framework`；训练入口仍由 framework 自持。这是下面所有准则的
物理基础。

## 1. 抽象原则

总原则：**一个抽象的净收益，等于它隔离的变化，加上它复用的共性，减去它引入的认知成本。**
下面把这笔账拆成六条可执行的判断——前四条是建立一个抽象的前提（头三条给出抽象值得建立的三种正当
理由：隔离变化、复用共性、统一异构产出；第四条是一道防止过度设计的闸门：必须有真实需求），后两条
约束抽象层之间的隔离与扩展。

### 建立抽象的前提

**1. 隔离一个方向的变化。** 抽象靠“容纳某一类变化”换取存在价值；先问它挡住了哪个方向的变化传播，
挡不住任何变化的抽象只是装饰。示例：`temporal/data.py` 的特征契约（检测框转 40 维向量）把数据集
格式的变化限制在数据加载层内部，流水线的训练与评估循环不受影响；两纵互不依赖，时序侧的数据格式
改动在物理上无法波及检测侧。

**2. 复用一份稳定的共性。** 只有当共性稳定、且差异集中在同一个维度上时，才抽取公共基类。两条时序
流水线的差异落在数据集构造、损失计算、推理循环三处，并不在同一维度，因此刻意保持为两个独立的扁平
文件；此前存在的 `feeding/` 策略层已被删除，正是从过度抽象回退的结果。判据：代码表面相似不构成复用
的理由；未来新增的流水线未必只在同一维度上变化，不应把当下的相似固化为长期契约。

**3. 统一异构产出，换取一致性与可解析性。** 处理异构本身就是抽象的价值所在：不同模型的指标与语义
各不相同，但只要它们产出同一种结构（`EvaluationResult v2`），下游——矩阵汇总，以及外部模型管理仓库——就能
在不理解任何单个模型的前提下统一解析、对比与消费。产出的一致性（可机读、可追溯）正是这层抽象要买
下的东西。但这里同样容易过度设计，且有两个相反的方向：

- **抹平差异**：为了“一致”强行把异构指标折算成单一的综合分数，或让 `N/A` 与 `MISSING` 混同。这是在
  值的层面过度统一，丢掉了本应显式保留的差异。
- **契约做得过重**：让信封或矩阵去理解每个模型的语义，或预先建一个穷举所有字段的庞大 schema。这是在
  结构的层面过度设计。

正确的分寸是让契约尽量薄：评估结果对指标语义保持无知，只承载三态单元格与身份列；矩阵动态取各模型指标列
的并集，而不是硬编码 schema。差异被如实保留并显式标注，既不抹平、也不为它建重型结构。具体不变量见 §2。

**4. 由当下的真实需求驱动，不为设想的未来预建。** 上面三种理由都必须对应一个此刻真实存在的调用方，
否则这道闸门就该拦下它。违反它就是最典型的过度设计——**抽象无人使用**（建了却没有任何调用方）：已删除的 `feature_schema.py`
中的 `FeatureSchema` 类从未被实例化，特征兼容检查实际由 `integrity.check_feature_schema` 以字典比较
完成。判据：任何抽象至少要有一个真实调用点，承担公共职责的抽象要有两个以上的跨模块使用者；删除前先
  检索调用点，确认无人调用即可删除。

### 抽象层之间的隔离与扩展

**5. 层与层之间保持清晰隔离。** 相邻的抽象层不应互相渗透：上层看不见下层的实现细节，各自职责不
越界。两纵一脊之所以成立就靠这一条。它有三个具体表现：

- **边界不向外泄漏实现细节。** 一个声称通用的层，必须真正隐藏它所声称隐藏的东西。违反它就得到另一类
  失败——**抽象泄漏**（这里的“泄漏”指抽象向外暴露了某个具体实现的细节，而不是指缺少抽象；它是边界不
  诚实、泛化不到位，而非“建多了”）：`apply_overrides` 曾写死 PyTorch 训练惯用的 `batch_size` 键，而
  ultralytics 读取的键是 `batch`，使
  该覆盖项对检测侧静默失效；现已改为通用的 `-S/--set` 点路径寻址。判据：审查通用层或脊柱层时，检查
  是否出现只有某一纵才理解的名词，若有即为泄漏。
- **每项语义只有一个归属者，组合优先于继承。** 监督口径与推理方式归流水线所有、不写入模型；模型若需
  携带自身的训练细节，通过可选的 duck-type 钩子（`fit_normalization`、`compute_loss`）暴露，流水线在
  钩子存在时调用、不存在时回退到默认路径，不为此引入基类。
- **必要的跨层耦合集中到单一组合根。** 有些依赖无法消除——总得有一处知道全部流水线；正确的做法是把
  它收敛到一个显式位置，而非散落各处。`core/registry.py` 是唯一同时依赖两纵的地方，脊柱与两纵因此都
  保持互不交叉依赖。

**6. 新增模型的接入点相对集中，不散落各处。** 接入一个新模型时要改动的位置应当收敛、可预测，而不是
牵动整条链路——这是上一条隔离到位后应得的扩展收益。接一个时序模型 = 新增一个 `nn.Module` 文件 + 在
`models/__init__.py` 注册表加一行 + 写一份实验配置 yaml，两条流水线、`data`、`metrics`、CLI 与脊柱都
不改动；接一个 YOLO 变体 = 只写一份配置、零代码。判据：如果接入一个新模型除了上述集中的少数几处、还
需要改动分散在多个文件的多处，说明接入点没有收敛。

## 2. 不变量（重构不得破坏）

- **结果三态**：`NOT_APPLICABLE`、`MISSING`、`COMPUTED` 三者严格区分，禁止用 0 冒充不适用。
- **checkpoint 不静默加载**：配置错配或 schema v1 sidecar 与权重摘要不一致时立即拒绝加载。
- **推理语义显式**：离线模型不伪造单窗模型前向基准，真实 pipeline/端到端延迟由后端测量。
- **异构矩阵不做综合评分**：允许不同模型拥有不同的指标列，不对跨类指标生成统一分数。
- **代码只产出事实**：完整性检查只说明评估结果是否可解释，是否达到业务标准由人判断。

## 3. 可操作的检查清单

- **建立抽象前**：它挡住了哪个方向的变化？没有就不要建（原则 1）。
- **抽取基类前**：差异是否落在同一维度、使用者是否达到两个以上、共性是否稳定？否则暂不抽取（原则 2）。
- **汇总异构产出**：差异是被如实保留并标注，还是被抹平（综合分／混同 N/A 与 MISSING）？产出契约是否
  保持对模型语义无知、足够薄，没有为异构建重型结构（原则 3）。
- **建立抽象前 / 删除代码前**：现在是否已有真实调用方？没有就先等需求出现，无人调用即可删除（原则 4）。
- **审查通用层或脊柱层**：是否出现只有某一纵才理解的名词（泄漏）？语义是否单一归属？跨层耦合是否集中
  在组合根？（原则 5）
- **新增模型时**：改动是否收敛到少数固定位置（新增实现 + 一处注册 + 一份配置），还是散落多处（原则 6）。
