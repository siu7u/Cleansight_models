# group1 检测：仓库里第一次**全量数据**训练（2026-10-12 起）

> 分支：`feat/yolo-group1`。回应用户目标里的"链路当中的 YOLO 提升"这一半。

## 0. 一句话

**此前 group1 的所有 run 都是 `fraction=0.2` 的探针**（15 轮、只用 20% 训练数据）——
包括各种文档里被当作"结果"引用的 mAP50 0.4271 那批。本轮起的是**仓库第一次
`fraction=1.0` 的 group1 全量训练**，且 ep1 就超出 registry legacy 的全量读数。

## 1. 先把上一轮的疑问查清（这是本轮第一件事）

上一轮我留了一个必须解释的差距：同一 `large_baseline` 配方，2026-08-10 的 ep1 是
mAP50 **0.4163**，本轮 ep1 是 **0.6208**，差 0.20。逐一比对 `args.yaml` 后**原因明确**：

| 键 | 2026-08 的 run | 本轮 |
|---|---|---|
| **`fraction`** | **0.2** | **1.0** |
| `epochs` | 15 | 150 |
| batch / imgsz / model / data / device / seed | 16 / 640 / yolo11n.pt / 同一 data.yaml / 0 / 0 | **完全相同** |

→ 那 0.20 是**"只喂 20% 数据"造成的**，不是数据集换代、也不是配方差异。

**并且这不是个别 run 的问题**：逐个扫 `runs/cleansight-yolo/opt-group1*` 的 `args.yaml`，
**全部 11 个历史 run 都是 `fraction=0.2` / `epochs=15`**（实际只跑到 9~15 轮）：

```
large_baseline   0.2 ×3        large_s        0.2 ×2
large_m_960      0.2           large_s_960    0.2 ×3
large_s_freeze   0.2           （本轮）large_baseline_lowmem 1.0 ← 第一次
```

**因此本仓库此前的 group1 读数一律是 smoke 口径**，按 `verification-first` 的纪律不得当作
模型质量结论；`docs/YOLO_OPTIMIZATION.md` 的目标（P/R ≥ 0.7）也从未在足量数据上被检验过。

## 2. 本轮的全量 run

配方 `large_baseline_lowmem`：yolo11n / 640 / batch 16 / 默认增强 / `fraction=1.0` /
150 轮 / patience 30 / workers 2（唯一相对 `large_baseline` 的变量是 worker 数，12GB WSL 需要）。
run：`runs/cleansight-yolo/opt-group1_large-large_baseline_lowmem-20261012-175339`。
**实测节奏（2026-10-12 第三次更正，见下）**：

> ⚠️ **`results.csv` 的 `time` 列是"累计秒数"，不是每轮秒数。**
> 判据：该列单调递增，且 ep17 的 `time=4148s（69.1 min）`与**进程 etime≈70 min 吻合**。
> 逐轮增量（相邻两行相减）才是每轮耗时：**min 228s / 中位 241s / max 257s ⇒ 每轮约 4.0 min**。

因此 **150 轮 ETA ≈ 10.0 小时**（按逐轮中位 241s × 150）。

| epoch | 累计 time | 该轮耗时 | val mAP50 | P | R |
|---:|---:|---:|---:|---:|---:|
| 1 | 272 s | — | 0.6208 | 0.6615 | 0.6423 |
| 2 | 521 s | 249 s | 0.5560 | 0.6338 | 0.6203 |
| 16 | 3891 s | — | 0.5350 | 0.6230 | 0.5710 |
| 17 | 4148 s | 257 s | 0.5880 | 0.6648 | 0.5939 |

**关于"节奏"我连续错了三次（如实记录，教训比数字重要）**：

| 版本 | 我的说法 | 错因 |
|---|---|---|
| 初版 | 4~5 min/epoch、约 10 h | 未计 setup（结论凑巧接近，但依据是错的） |
| 第 2 版 | 5.5 min/epoch、约 14 h | 把 ep1（含一次性 setup）当成每轮成本 |
| 第 3 版 | **8.7 min/epoch、约 21.7 h** | **把"累计 time"当成了"每轮 time"** —— 高估 2.2 倍 |
| **本版** | **4.0 min/epoch、约 10.0 h** | 用**逐轮增量**，并与进程 etime 交叉核对 |

根因是同一个：**在没确认某个列/字段的含义之前就据它推算**。以后凡是要从 `results.csv`
这类外部产物推数量，先做一次"与该行其他字段或进程状态交叉验证"再写结论。

**读 ep1 → ep2 的回落**：mAP50 0.6208 → **0.5560**。这是早期训练的正常波动
（且 ep1 偏高本身有运气成分），**不能**用 ep1 单点去比任何基线——本文 §2 表格里那个
"ep1 已超出 legacy"的说法只作**过程观察**，**不作为结论**。真正的对照要等收敛后（或早停点）。

## 3. 中期状态（2026-10-12 19:58，ep29/150）：`best.pt` 的选择指标不是 mAP50

要看懂"best.pt 是哪一轮"，必须先确认**选点指标**。ultralytics 默认
`fitness = 0.1·mAP50 + 0.9·mAP50-95`，**mAP50-95 权重是 mAP50 的 9 倍**。按 row 各自算峰值：

| 指标 | 峰值轮 | 值 |
|---|---:|---:|
| `metrics/mAP50(B)` | **ep1** | 0.6208 |
| `metrics/mAP50-95(B)` | **ep28** | 0.2383 |
| ultralytics **fitness** | **ep28** | 0.2753 |

`best.pt` 的 mtime（19:50）与 ep28 落盘时刻一致 ⇒ **`best.pt` = ep28**。

> **我这里先读错过一次**：一开始只看 mAP50 峰值，得出"best.pt 仍指向 ep1"，
> 进而推出"这个 run 白跑了 29 轮"。核对 fitness 后才发现峰值在 ep28。
> 教训：**说"best 是哪一轮"之前，先确认该框架的选点指标是什么**——
> 这和本任务前几次"不确认字段含义就推算"是同一类错误（ULT 的 `time` 列那次也是）。

### 读数（`best.pt` = ep28，val）

|---|---:|---:|---:|---:|

但**读数纪律不变**：① 与 registry 那行不是同数据视图，不能说成"同口径改进"；② 才 ep29——
若 fitness 峰值维持 ep28，`patience=30` 下约 **ep58 早停**（约再 29 轮 × 4 min ≈ 2 小时），
届时才有可登记的收敛读数。
