## 4. 隐性假设与替代解释

### 4.1 统计口径问题（文档把"seed 级显著性"当成了什么）

1. **seed 不是独立重复。** 32 个 seed 共享同一 train/val/test 划分、同一数据版本、同一超参、
   同一推理协议、同一台 GPU/框架版本。配对 Wilcoxon 把"32/0，p=7.9e-7"写成主证据，
   但**唯一能回答"换一批视频/换批次是否还成立"的统计单元是视频或批次**（我算出：视频级 p=0.0234，
   符号检验 0.070）。文档 §9.2/§9.4/§9.2c 的所有 headline 都是 seed 级；视频/划分级证据被推给课题⑩。
   **不是造假，是口径错配**：`p=1.8e-05` 与 `p≈0.02~0.07` 描述的是两个不同命题。
2. **bootstrap CI 只覆盖 seed 抽样不确定度。** 从同一 32 个 seed 里重抽样，无法产生"换 test split"
   的方差；`[+3.34,+5.11]` 因此**系统性偏窄**。文档 §9.2c 用"区间包含 +5.00"作判据，
   这在"只换 seed"的世界里成立，在"换批次"的世界里未定义。
3. **8-seed 噪声地板本身只由 3 个观测估计**（A/B/C 三段），用它反推"±0.7~1.3pp"再推"需 ≥16/32 seed"，
   是把 n=3 的极差当标准误。实测 bootstrap 中位 sd 是 0.60(n=8) / 0.48~0.51(n=16) / 0.36~0.40(n=32)。
4. **同一页混用两种统计量。** §9.2b 用"臂中位 58.20 < 58.31"推翻调度，
   而同一批数据的**配对 Δ 中位是 +0.36pp（支持调度）**；§9.2c 又在 "+4.47（配对）" 与
   "+4.41（臂中位差）" 之间来回切换。文档应在每处声明用的是哪一种。
5. **`best_metric` 只有 4 个 val 视频**（§9.3 自己指出），而 §9.3 用 8-seed 的 test 差（+1.19pp）
   判断选点泄漏是"白拿 ≈1pp、与噪声同量级"——方向正确，但那 1.19pp 本身也没有视频级/划分级检验。

### 4.2 "同一 test split 被反复用于选型"的乐观偏差

- **缓解（真实存在）**：R6 明确声明 v4 的**通道集**（`c,a,w,h`）是"只看源域表 + 维度不过大"选的；
  17 个候选的对比也走源域 30 折（`foldcheck.py::part_b`）。这一层纪律比多数项目更严。
- **残留泄漏（文档未在任何地方统一说明）**：
  1. v4 的**布局**（热 3×3 / 冷 1×1）承自 v2，而 v2 是第 4/5 轮**在这个 8 视频 test**上比出来的
     （R5 §4 的选点口径表就是在 test 上比 `val_edit/val_f1_0.25/val_f1_0.1`）；
  2. v4 落地后的**"全栈"配置**（mindur15）是**在同一 test split 上被反复观察过的**（R6 已用过一次）；
  3. §9.2d 的全栈 59.30 是"val 选点"，但 val 只有 4 个视频，选点噪声与 8-seed 噪声同量级；
  4. "v4 是全仓最强"这一事实本身是 16 条轴 / 17 候选在同一 test 上的**多重比较**产物。
  → 因此 `+4.4pp` 是"**在这一次划分上、经多候选筛选后**的效应"；文档 §9.2/§9.4 没有传递这个限定，
  只在课题⑩里以 `LOO [+2.85,+5.75]` 形式出现。

### 4.4 其它隐性假设

- **`edit` 的语义**：`edit` 对段数敏感、对时长不敏感（文档已声明）。因此"`edit` −7.93pp"
  不能直接读作"分割质量下降 7.93pp"——v4 的**序列错配项其实改善 2.36pp**。
  §9.4 的标题"`acc` 涨、`edit` 跌"若被外行引用，容易被读成后者。
- **"帧级 vs 段级取舍"的选型建议**（§9.4 判读 3）没有给出**下游消费粒度**的实证数据
  （仓库里没有下游事件的消费链路），因此仍是规范性建议而非实测结论 —— 文档已用【建议】标出。
- **"全部 +4.4pp"的主语**：文档写得很清楚（非因果整段 `mstcn2`），但 §0.5/§0.6 的摘要顺序
  会让人先记住 +4.4pp 再看到边界；建议把"离线整段"提到第一条。
- **`acc` 的绝对值本身低于平凡基线**（v1 53.90 < 55.25；全栈 v1 54.83 < 55.25）——
  §9.1a 说了"基线低于地板"，但 §9.2d 在同一页把 54.83 当作"同协议基线"正常使用，未重复该提醒。

## 5. ⑪ 离线→流式差距：现有可跑链路清单与命令

### 5.0 结论先行

- **v4 契约（128 维）+ 因果架构的 checkpoint 与配置：不存在**（`framework/experiments/` 无
  `gru-*-roi-v4*.yaml`；`runs/acc-push/` 下无任何 `gru-*`）。因此"v4 在流式下的收益"**确实无任何实测**——
  文档 §11.2 的自述成立 ✅，而且**不做训练就无法补上**（本审计不允许训练）。
- **但"离线↔流式"这个轴本身仓库里有实测**，且量级不小（见 5.1）：**同一 checkpoint 换喂法就能让
  acc 变 +3.7pp、edit 变 −3.7pp（gru），最极端 acc +24.8pp（transformer）**。这比文档"未经验证"的
  中性表述更值得引用：**喂法轴的影响量与 4.4pp 主效应同量级甚至更大**。
- **v1 契约（144 维）上有一条真实可跑的流式对照链路**（5.2）：现成的 GRU checkpoint 用的是
  `sliding_window_temporal`，但它的 testset 是**旧 revision、只有 2 个视频**，读数（acc 50.77）
  **不可与 53.90 相减**。要得到可比的流式读数，需按 5.2 的命令重评（该命令会写入 run 目录，
  故必须先拷贝到可写目录）。

### 5.1 链路 A：`benchmark/temporal_feed_mode/`（**已跑过，有正式产物**）

|---|---|---:|---:|---:|---:|---:|---:|
| gru（因果） | legacy-20d / Endo_Project（34775 帧、4 视频、`test.split1.bundle`） | 87.29 | **91.00** | 41.62 | **37.92** | 91.54% | 12.99 ms |

### 5.2 链路 B：ROI-v1(144 维) 契约上的因果 GRU —— **唯一的现成 checkpoint**

现成产物：`runs/strategy_compare_gpu/gru-20260904-140517/`（`gru` h128×3，`input_dim=144`，

```bash
# ⚠️ formal 评测会把 artifacts/ 与 checkpoints/*.eval.md 写回 run 目录，破坏本审计的只读约束；
#    因此先拷到可写目录再评。不要直接在 runs/ 下跑。
cp -r runs/strategy_compare_gpu/gru-20260904-140517 tmp/deepdive/gru-roiv1-stream
```

**两个必须随读数引用的坑**：
1. 该 checkpoint 的 `best.pt.meta.json` 记录 testset = `temporal.actionmixed-auto-roi-v1`
   **revision `b7edb874…`、`num_items = 2`**；而当前 catalog 里同名 dataset 的 revision 是
   **`6375eba9…`、test = 8 视频 / 2639 帧**。`benchmark/cli/eval.py` 的
   `check_feature_schema` 只校验 `dim`，**不校验 dataset revision** → 重评会**在新划分上评旧权重**，
   必须显式声明"跨数据集版本"。
2. 我**实际启动了这条命令**（CPU，输出到 `tmp/deepdive/gru-stream-eval/`），**≥19 分钟未产出任何文件**
   （沙箱 PID 命名空间下 `ps` 看不到该进程，无法判定是"慢"还是"卡"）→ 本审计**主动终止**，

   （逐 tick 前向，2639 tick），这与 §11.3 清单 5 的延迟/吞吐缺口是同一件事。

### 5.3 链路 C：同一 checkpoint 的"全序列 vs 滑窗"同契约对照（推荐）

把 5.2 的 config 复制一份、只改 `pipeline`，即可对**同一个因果 checkpoint**做两种喂法，
这是仓库里唯一能做到"同 checkpoint、同契约、同划分"的离线↔流式对照：

```bash
sed 's/^pipeline: sliding_window_temporal/pipeline: full_sequence_temporal/' \
    framework/experiments/gru-actionmixed-auto-roi.yaml > tmp/deepdive/gru-roiv1-fullseq.yaml
# 流式侧（滑窗 + 因果平滑）
python -m benchmark.cli.eval --config framework/experiments/gru-actionmixed-auto-roi.yaml \
  --ckpt tmp/deepdive/gru-roiv1-stream/checkpoints/best.pt --out-dir tmp/deepdive/eval-stream
# 全序列侧（同一权重，逐帧 argmax、零平滑）
python -m benchmark.cli.eval --config tmp/deepdive/gru-roiv1-fullseq.yaml \
  --ckpt tmp/deepdive/gru-roiv1-stream/checkpoints/best.pt --out-dir tmp/deepdive/eval-fullseq
```
注意因果模型进 `full_sequence_temporal` 是合法的（`causal=True` 只约束滑窗侧）；
**非因果 `mstcn2` 进滑窗侧会被拒**（`models/__init__.py` 的 `causal` 标志），所以
"v4 契约的离线↔流式"**必须**先训一个 v4 因果模型（本审计禁止训练）。

### 5.4 链路 D：离线补后处理（不训练、立刻可跑）

`tools/probe_offline_postprocess.py` 已声明口径：`offline-argmax`（现行正式口径）vs
`offline+median{k}` / `offline+mindur{d}`（新口径），其中 `smoothing_min_duration` 只存在于
**滑窗**流水线，而离线侧是"零平滑"——这正是 §11.2 的第 ③ 条差异。可用它把"平滑"这一项的差距量化：

```bash
python tools/probe_offline_postprocess.py --run "runs/acc-push/acc-roiv4/h128/mstcn2-*"
```
（注意其自述：在 test 上挑最优 k/d 属于用测试集选参，落地前须在 val 上选。）
